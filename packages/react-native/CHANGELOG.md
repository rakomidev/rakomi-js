## 0.4.0 — 2026-09-07

- `AuthError` (the shared error type returned by `@rakomi/react` and `@rakomi/react-native`'s sign-in, sign-up, magic-link, email-OTP, MFA, password-reset, and profile calls) now carries an optional `requestId` — the same per-request correlation id the API logs and returns via `X-Request-Id` — when the failed call's response provided one. Hand it back to Rakomi support to correlate a caught error with a server-side log line. Additive and absent (never fabricated) when the server did not emit one; no existing `AuthError` variant changes shape otherwise.
- Fix MFA (TOTP) sign-in completion, which could never succeed: `POST /v1/auth/mfa/verify-login` requires the `X-API-Key` header like every other `/v1/auth/*` endpoint, but neither `@rakomi/sdk-core`'s `verifyTotp` nor `@rakomi/react`'s internal `verifyMfaLogin` sent it, so the request was always rejected before the code was even checked. `@rakomi/react`'s implementation additionally posted the request body field as `challenge_token` instead of the `mfa_challenge_token` name the endpoint requires, which alone would have failed validation. `@rakomi/sdk-core`'s `verifyTotp` now takes a required `apiKey` parameter (supplied automatically by `@rakomi/react-native`'s `useMfa()` hook and `<SignIn>` component — no consumer-facing change there); `@rakomi/react`'s `<SignIn>` MFA step now sends both the header and the correct field name. Both packages also now surface the server's actual `application/problem+json` `detail` message on a failed verification instead of a generic status-code string.
- Fix `<RakomiProvider>` reporting a signed-out session on the very first mount under React `<StrictMode>`, even with a valid session already persisted from a previous app launch. The provider's cold-start restore effect called `restore()` on its token runtime and destroyed that same runtime in the effect's cleanup; under `<StrictMode>`'s dev-only mount→cleanup→mount double-invoke, the second `restore()` call landed on the already-destroyed runtime and was silently treated as "no session" regardless of what was actually in storage. The restore call is now guarded so it runs exactly once per runtime instance. Found while cross-checking a related fix in `@rakomi/react`.
- Fix `<SignUp>`'s registration call, which could never succeed: its `onSubmit` posted directly to `POST /v1/auth/register` without the `X-API-Key` header, and that route is behind `apiKeyAuth()` like every other `/v1/auth/*` endpoint — the same class of defect the `<SignIn>` MFA fix closed. The request is now sent with the provider's `publishableKey` as `X-API-Key`, and a failure now surfaces the server's real `application/problem+json` `detail` message (and `request_id`, when present) instead of a generic status-code string. Audited every other `/v1/auth/*` call site in this package (`useAuthConfig`, `useMfa`) — both already send the header; `<SignUp>` was the only gap.
