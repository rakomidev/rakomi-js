## 0.10.0 — 2026-10-16

- **A token refresh answered with a 5xx other than 503 and 521–523, or one that gets no response, is retried once, immediately — and if that does not settle it, the session ends instead of being retried later.** The server may have rotated the refresh token before it failed or before its answer was lost, and it hands that rotation back only to an identical retry (same client, same network address and user agent, same DPoP key) within 10 seconds. The SDKs now send that one retry at once, with a fresh DPoP proof from the same key on a bound session, when the first failure arrived within 8 seconds. If the retry is neither a success nor a definitive rejection (another 5xx, a 503, a 429, a network failure), the outcome is unknown and the session ends: before, the failure was transient and the same refresh token was sent again with backoff — after the window, a rotated token sent again is a reuse, and the server revokes every session of the user. A 503, 521–523, 429 or 408 is unchanged: transient, the session kept. **Breaking:** a network failure on the first request is no longer transient on its own — it gets the same one immediate retry, and two in a row end the session.

## 0.9.0 — 2026-10-13

- **Breaking: `credentials.list()` pages with a cursor.** `GET /v1/credentials` no longer takes `offset`. Pass `cursor` (the previous page's `pagination.next_cursor`) instead; the result now carries `pagination: { next_cursor, has_more }`. **Action needed** if you passed `offset`: loop on `pagination.next_cursor` until `has_more` is false.
- **DPoP: set `middleware({ dpop: { origin } })` in production, and read `details.reason`.**
- **Breaking:** `client.link.initiate()` no longer takes `mfaVerificationToken`. The API never read the field it was sent as, so no working call changes at runtime; the break is compile-time only.
- **Token endpoint errors: read the sub-reason from the RFC 6749 §5.2 form.**
- **The client accepts publishable API keys.** `new RakomiClient({ apiKey })` now accepts the `akp_live_` and `akp_test_` prefixes of publishable keys (an `akp_test_` key selects the test environment, like `akm_test_`). Secret `akm_` keys are unchanged. Use publishable keys only where the key is visible to end users; keep a secret key on your server.
- **Breaking:** `VcCredentialResponse.user_id` is now `string | null` (a type change). It was previously typed as a plain `string`. A verifiable credential's subject can now exercise their right to erasure (e.g. an account-deletion request) while the credential record itself remains listable/fetchable — its revocation history and status-list position are still meaningful to other holders and verifiers. `user_id: null` on a listed or fetched credential means the holder's account no longer exists.
- Security: new opt-in `strictEnvironment` option on `RakomiClient` hardens `verifyToken()` against tokens that carry no `rkm_env` environment claim.
- **Breaking: `WebhookEvent` describes the body Rakomi actually sends.**
- **Webhook verification accepts `whsec_` secrets (Standard Webhooks).**

## 0.8.0 — 2026-10-04

- `token/invalid_issuer` no longer suggests that every token is issued by `api.rakomi.com`: its suggestion now says the token `iss` must equal the configured issuer exactly — the issuer of the environment whose tokens you accept.
- **Breaking: signing keys are read from the expected issuer's own `jwks_uri`.** `RakomiClient.verifyToken()`, `verifyRakomiToken()` and `verifyLogoutToken()` no longer fetch a fixed `/.well-known/jwks.json`. Each resolves the issuer's discovery document (OAuth 2.0 Authorization Server Metadata first, then OpenID Connect Discovery, both path-aware for an issuer such as `https://api.rakomi.com/t/<tenant>/<environment>`), checks that the document names exactly that issuer, and verifies only against the keys at its `jwks_uri`. A token signed with another issuer's key is rejected, even if its `kid` is valid elsewhere.
- **A token-endpoint outage is a typed transient error, not `oauth/invalid_request`.** When `/oauth/token` answers 5xx, 429 or 408 — whatever the body, including a proxy's HTML error page — `exchangeCode()`, `refreshToken()`, `rotateRefreshKey()` and the device-flow poll now return the new `oauth/temporarily_unavailable` error (`ERROR_CODES.OAUTH_TEMPORARILY_UNAVAILABLE`) with the HTTP `status` and, when the server sent `Retry-After`, `retry_after_seconds`. The grant or refresh token is still good: keep the session and retry. Other token-endpoint errors now carry `status` too.
- **Breaking: DPoP-bound access tokens now need a valid DPoP proof to verify.** A token carrying `cnf.jkt` (RFC 9449) is rejected with the new error code `token/invalid_dpop_proof` unless the request's DPoP proof verifies for that token and that key. Previously `verifyToken()`, `verifyRakomiToken()` and `middleware()` checked only the token itself, so a DPoP-bound token was accepted without a proof.

## 0.7.1 — 2026-09-29

- **Security fix: unknown-`kid` JWKS refreshes are rate-limited.** Previously every token carrying a never-seen `kid` forced a fresh JWKS fetch, so a stream of forged tokens with random `kid` values turned `verifyToken()` / `verifyRakomiToken()` into an amplifier of requests against the JWKS endpoint. While the cached key set is still fresh, an unknown `kid` now triggers at most one refresh per 30-second window; further unknown `kid`s inside that window are rejected with `jwks/no_matching_key` without a network call.
- **Security fix: a non-finite tolerance no longer disables expiry or replay checks.** Passing `NaN` (for example from `Number(process.env.SOME_UNSET_VAR)`) as `clockTolerance`, `webhookTolerance`, or a per-call `verifyWebhook(..., { tolerance })` previously slipped through the range clamp and made every "too old" comparison false: `verifyToken()` accepted expired tokens and `verifyWebhook()` / `verifyPublisherWebhook()` accepted webhook timestamps of any age. A non-finite value (`NaN`, `Infinity`, `-Infinity`) now falls back to the documented default (30 s for tokens, 300 s for webhooks); the standalone `verifyWebhook()` applies the same 300 s fallback.
- **Security fix: webhook verification rejects an empty signing secret.** `verifyWebhook()` (standalone and `client.verifyWebhook()`) previously used an empty or whitespace-only plain-string secret as the HMAC key. An empty key is publicly known, so a forged webhook signed with it verified successfully — typically the result of an unset environment variable. A missing, empty or whitespace-only secret now returns `{ ok: false, error: { code: 'webhook/invalid_secret' } }` for every request.

## 0.6.0 — 2026-09-13

- Adds `verifyLogoutToken()` — a standalone helper (no `apiKey`, no `RakomiClient`) that verifies an OIDC Back-Channel Logout 1.0 `logout_token` your `backchannel_logout_uri` endpoint receives. It performs every §2.6 validation step this SDK can decide on its own — signature and algorithm (RS256 only, `alg: none` rejected), `iss`/`aud`/`iat`/`exp`, presence of a `sub` or `sid` claim, the `events` claim's fixed member, and rejection of a `nonce` claim (explicitly forbidden for Logout Tokens) — and returns the same never-throws `{ ok, data | error }` shape as `verifyRakomiToken()`.
